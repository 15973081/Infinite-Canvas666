## 性能基线

工具 [canvas_frontend_benchmark.cjs](../tools/canvas_frontend_benchmark.cjs) 以原生产页面/脚本在同一 headless Chrome 下测量。基线从 `git archive ae150ab static` 导出到本地忽略目录；当前前端代码为 `33c6898`（网关兼容修复不改变前端字节）。保存原始样本、环境和 p50/p95，见 [性能记录](canvas-frontend-performance-2026-10-05.json)。

每套画布为 25×40 网格的 1000 个文本提示节点、999 条链式连接；Classic 管理列表另有 2000 个画布、100 个文件夹。每个操作预热 2 次、测量 20 次，两版本按 Classic 基线→当前、Smart 当前→基线执行。记录同步操作与强制布局耗时，后续两帧稳定后再取下一样本；后续帧本身未计入。

局部命令为 Classic `refreshNodes(['node-0'])`、Smart `refreshSmartNodes(['node-0'])`。Smart 按原依赖规则扩展到这条链的全部 1000 个目标，Classic 仅指定节点；不能横向将两者当成同一种单节点刷新，也不能将 Smart 的高耗时简单归因于框架。两版本在各自同一数据/规则下纵向比较。

首批夹具遗漏 Classic 连接 ID，虽然业务数组有 999 条，实际缓存仅保留一个条目。首批结果作废，留于本地 `.local/assessment-invalid-link-id.json`；补齐唯一 ID，并断言 1000 个节点元素、999 条实际连线及平移 DOM 复用后重跑。本报告仅采用修正后的采样。

环境为 Windows 10.0.19045、Ryzen 5 5600XT / 12 逻辑核、Node 24.18.1、Headless Chrome 153、1280×900。所有版本均检查 1000 个节点元素、999 条实际连线、平移后目标 DOM 保留；测量内渲染操作未触发保存（工具隔离了写入，不代表所有业务操作不保存）。

## 迁移判断

**本次评估不启动 React 实施。** 已验证的命令/所有者、通信接口和纯模型为以后局部迁移提供入口；当前没有一个已确认的 UI 开发需求或维护收益足以抵消构建、混合 DOM 管理、事件接管和缓存部署的新增成本。性能与真实服务结果决定后续验收条件，不构成“换框架会更快”的证据。

若未来确定需要局部试点，Classic `gateCanvasList` 是可讨论的候选：消费已派生模型，通过现有具体业务命令操作，DOM 容器由一种呈现实现独占，保留外侧目录/菜单、权限、保存及动画行为。需先列清事件与 DOM 交接、回滚原呈现入口，并在相同基准及真实成员服务下比较；不是直接让 Hook 拥有文档、保存或 WebSocket。

React 官方支持在已有页面内挂载局部根；`createRoot` 会接管根内 DOM，卸载也需明确执行。因此原生渲染器与 React 不能继续同时写同一容器。这只说明技术路径可行，不证明此项目现在值得迁移。[接入已有项目](https://react.dev/learn/add-react-to-an-existing-project)、[createRoot](https://react.dev/reference/react-dom/client/createRoot)（2026-10-05 核对）。

保存/撤销、锁/同步、生成任务和服务端一致性保持独立事项，并非必须先全部重写。以后正式决定试点时，外部生成服务和生产环境验收仍需要明确测试目标与资源范围；本次不为补齐文档而执行未限定的收费请求。
