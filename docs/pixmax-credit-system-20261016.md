# Pixmax 积分体系清洗与提取

核验日期：2026-10-16。目标站：<https://app.pixmax.cn/?space=personal>。线上版本：`release/1.36.4_261015(2020)`。

本轮仅提取业务规则、数据配置、页面结构和后续验收边界，没有编写积分功能、修改应用代码或执行数据库迁移。以下是 Pixmax 的观察结果，不表示 Infinite-Canvas666 已具备这些能力。

## 1. 可以采用的国内站基线

国内个人空间目前以按量充值为主：人民币购买积分，生成任务消耗积分；充值、赠送、消费、到期分别记录。钱包总额、发放批次、积分流水、任务费用、人民币订单是不同层次的数据，不能合并为一张费用表。

证据分级：**已核实**表示当前页面或成功接口响应可见；**前端规则**表示公开前端有相应计算或控制逻辑，未验证服务端执行；**待核实**表示不能从现有证据确定。

## 2. 充值档位、取整与活动

以下为当前 FREE 账户对应的国内充值方案，未套用其他会员档位或优惠码。

| 人民币金额 | 基础积分 | 加赠比例 | 加赠积分 | 普通到账 | 符合首充条件时到账 |
|---:|---:|---:|---:|---:|---:|
| 69 | 1,035 | 15% | 155 | 1,190 | 1,690 |
| 399 | 5,985 | 30% | 1,795 | 7,780 | 8,280 |
| 2,499 | 37,485 | 50% | 18,742 | 56,227 | 56,727 |
| 4,999 | 74,985 | 70% | 52,489 | 127,474 | 127,974 |

69 元的充值汇总和四张档位卡已在页面核对；其他首充到账值为已提取公式推算，不是实际购买结果。

前端计算规则（S5）：

1. 基础积分＝向下取整（充值金额 × 当前方案兑换比例）。
2. 按金额从高到低寻找满足门槛的加赠档位；未命中则使用方案默认加赠率。FREE 默认加赠率为 0。
3. 加赠积分＝向下取整（基础积分 × 加赠率）。基础与加赠分别取整。
4. 到账积分＝基础积分＋加赠积分＋符合资格的首充奖励。
5. 活动充值使用独立的 `creditsPerAmount` 和 `bonusRate`；匹配活动金额、剩余购买次数等条件，不能与普通阶梯直接混算。本次活动列表为空。

其他金额输入存在值得保留的前端不一致：国内支付门槛常量为 0.5，输入处理却移除非数字字符，最大输入值为 1,000,000；小数金额能否正常购买未核实。不能直接把最低充值写成 10 元，也不能宣称已支持 0.5 元付款。后续应确定自己的输入精度与最低金额，不复制这一矛盾。

优惠码与兑换码应分开：优惠码参与待支付订单金额，前端在金额变化后要求重新输入；兑换码是独立的积分兑换入口。仅核对入口、接口及文案，没有提交优惠码、兑换码或测试真实支付。券与首充、加赠的完整叠加规则仍待核实。

## 3. 积分获取和有效期

| 来源 | 当前可确认的规则 | 边界 |
|---|---|---|
| 普通充值、充值加赠 | 按第 2 节规则；当前配置永久有效 | 不是所有活动都永久 |
| 首充赠送 | 达门槛且资格成立时 500 积分，当前永久 | 领取幂等和支付后发放时点未验证 |
| 邀请注册 | 邀请人 10 积分，被邀请人 10 积分；最多邀请 20 名好友；页面说明注册成功发放且永久有效 | 没有实际邀请或注册测试 |
| VisionTV 投稿 | 页面说明审核通过且作品 60% 以上由 Pixmax 完成，最高 10,000 积分 | 不是每次固定奖励，审核口径和到账时点待核实 |
| 注册、平台、客户测试、运营调整 | 当前发放记录和词典存在这些来源 | 注册默认数额及后台审批规则未证实 |
| 订阅、邀请订阅、会员购买 | 词典/API 保留，邀请订阅奖励配置本次为 null | 不作为当前国内开放政策 |

有效期不是单一钱包字段，而是每次发放的属性。前端支持：

- `PERMANENT`：永久。
- `FIXED_TIME`：指定日期失效。
- `AFTER_GRANT_DAYS`：发放后若干天失效。

基础充值、加赠、首充分别有有效期配置；不能将“当前充值永久”推广成“所有积分永久”。充值明细有开始时间和过期时间；前端将缺失开始时间显示为立即生效，将缺失过期时间显示为永不过期。钱包概览可分别提示购买、会员和赠送积分最近到期的数量与时间。

完整来源枚举见 `labels-and-enums.json`，共包含充值、活动充值、首充、平台赠送、创作扶持、超创计划、客户测试、内部使用、渠道合作、订阅、注册、首次下载、调研、邀请、兑换码、VisionTV、管理员调整、企业转入等来源。枚举存在不等于当前都可领取。

**未证实：**先到期先扣还是其他扣减顺序；退款回到哪个原批次；到期积分是否可恢复；不同批次跨任务预占方式；历史赠送的默认期限。

## 4. 模型消耗计价

清洗后有 74 条 `TASK_PARAMS`、4 条 `INPUT_TEXT`。按原始节点类型分为图像 21、视频 35、文本 13、音频 6、3D 2、缺失类型 1；没有擅自补全缺失类型。

### 4.1 可确认的前端报价方式

**参数计价：**按 `selectedParams` 的顺序取参数值，以 `||` 组成组合键。没有选定参数时走 `basePrice`；有参数时读取组合价格。`isPerSecond` 生效时再乘输出时长，随后乘生成数量。原矩阵的空参数仍保留，例如 `1080P||` 不与 `1080P||30FPS` 合并。

**输入视频：**启用 `isInputVideo` 且存在输入视频时选择 `combinationPricesWithVideo`；启用 `isInputVideoPerSecond` 时可能另加输入视频时长 × 对应输入单价。不能把输入视频价和普通生成价去重成一个值。

**素材附加费：**图像、视频、音频数量分别乘对应附加单价。前端中附加费与生成数量相乘的主价分开相加，不应在需求中擅自改成“所有费用都乘批量数”。最终以服务端报价与结算为准。

**文本长度计价：**前端预估为 `max(ceil(文本长度 / unitChars) × basePrice, minPrice) × 数量 + 素材附加费`。原实现用 JavaScript 字符串长度，不等同于 tokenizer 的 token 数，也不一定等于用户感知字符数。

**折扣：**保留折扣类型、比例、活动起止时间、响应中的服务器时间，以及 `returnDiscountedPrice`。活动时段有效时才应用；用户折扣另有是否返回折后价的判断。前端折后总预估使用四舍五入且至少 1 积分。不要把 0.6 当作固定原价，也不要把每秒价先取整再乘时长。

**独立报价：**图片放大、视频超分还有服务端估价接口。`pricing-configs` 不足以覆盖全部特殊操作，更不能据此推算创作助手实际 token 单价。

## 5. 钱包、流水和账单结构

| 层次 | 来源 / 关键字段 | 用途与限制 |
|---|---|---|
| 钱包余额 | `/credit/balance`：`accountType`、`totalBalance`、`transferableBalance`、`userTier`、`subscriptionCreditBalance`、`subscriptionCreditList`、`rechargeCreditBalance`、额度字段 | 顶部余额和账号可用额度；不同余额字段不能默认相等 |
| 钱包概览 | `/credit/overview`：购买、赠送、可选会员余额与各自最近到期信息 | 展示余额构成；不存在的字段不应自动解释为 0 |
| 发放批次 | `/credit/grants`：`source`、`totalAmount`、`remainingAmount`、`startTime`、`expireTime`、`createTime` | 充值明细实际也包括赠送批次，不只是付费订单 |
| 积分变动 | `/credit/transactions`：`type`、`amount`、`balanceAfter`、`transactionUuid`、任务、项目、团队、子账号、模型、业务原因、转赠双方 | 完整追踪入账、消费、到期；金额符号由类型决定 |
| 任务结算 | `/credit/consumptions`：`estimatedCost`、`actualCost`、`owedAmount`、`totalCost`、状态、任务与流水关联 | 预估、实际、欠费、总额四个字段必须保留，不能凭字段名猜加总公式 |
| 创作助手 | `/credit/agent-transactions` 与 `/turns`；页面按会话、轮次、账号、项目、模型、扣费、token 展示 | 当前账户返回空列表；内部完整行结构及 token 单价尚未验证 |
| 人民币订单 | 账单发票入口；订单号、时间、类型、状态、金额 | 金额订单与积分流水分别记录，退款状态不能替代退积分规则 |

页面布局已核对：账户管理左侧包括个人资料、积分充值、账单发票、积分明细、任务明细、企业认证。积分明细下有消耗明细、创作助手、充值明细。任务明细列出任务 ID、模型、时间、状态、积分消耗。

积分流水类型为 `ADD`、`DEDUCT`、`EXPIRE`；企业转赠还通过业务类型和转入转出方向区分。发放批次用独立来源枚举。前端保留 `PENDING`、`PAID`、`COMPLETED`、`CANCELLED`、`EXPIRED`、`REFUNDED`、`PAYMENT_MISMATCH`、`PENDING_IN_CACHE` 等订单状态，不能把支付成功页当作积分已到账的唯一证明。

抽样任务中存在失败且消耗为 0 的记录。这只能证明这些样本结果，不能证明所有失败都自动退款、退款即时到账，或证明后台一定采用“预扣后退”。

## 6. 企业权限、子账号和积分转赠

这一部分主要来自前端逻辑、余额字段和错误码；没有管理员后台访问或转赠实测。

- 主账号余额、团队额度、子账号额度分别有不足提示。余额有 `quotaMode`、`quotaAmount`、`quotaBalance`、`availableQuota`、周期与重置字段。
- 前端展示无限、固定、周期额度；周期包括日、周、月。企业服务端实际扣减顺序、跨团队额度关系和重置时区待核实。
- 充值入口对主账号与子账号有不同控制；不能仅隐藏按钮就视为服务端权限已完成。
- 转赠数量要求正整数，且不得超过 `transferableBalance`。接收对象使用 UUID 与名称核对。
- 转赠文案说明不可撤回；永久积分支持转赠，限期及限时活动积分不支持。转赠还涉及企业范围和资格，当前不可仅凭文案承诺所有普通账户可转赠。
- 手机或邮箱验证通过后，前端文案说明当前设备 4 小时免验证；有设备标识和验证状态接口。验证与转赠请求未执行。
- 企业转入是独立发放来源；转入、转出保留双方关联，不能只改两边余额而无流水。

管理员充值、赠送、调整的来源枚举已找到，但权限矩阵、审批、可操作额度、审计留存和撤销机制没有证据，作为待核实项。

## 8. 对照后续设计的验收边界（尚未实现）

“全部对照”应保留完整功能目录，同时将当前国内生效规则、可配置扩展和证据缺口分开。可按四个独立验收包推进：

| 优先级 | 验收包 | 必须能独立验证的结果 |
|---|---|---|
| P0 | 积分钱包、批次、流水 | 购买/赠送分类、批次有效期、余额与流水可对账；账号隔离；到期有记录；明确扣减顺序 |
| P0 | 模型报价、消费结算 | 参数变更重新报价；保留原价及折扣；防重复扣款；任务与流水关联；失败/取消/重试有明确且可测的处理规则 |
| P1 | 充值、奖励、支付订单 | 四档取整正确；首充资格只发一次；回调幂等；未支付不入账；金额校验；优惠码变更与活动有效期可追踪 |
| P1 | 管理员、团队额度、转赠 | 服务端权限；主账号/团队/子账号分别验收；转赠验证与额度；管理员调整留审计；跨标签切换账号不能串账 |

这里的防重复扣款、回调幂等、原子记账等是本项目应验收的工程要求，不是已证实的 Pixmax 内部实现。当前美元/人民币费用记录也不能直接乘 15 转成历史用户积分：原始成本、用户售价和积分消费是不同口径，历史转换及对账方案需要单独确定。

进入实现前仍需确定：积分扣减顺序；预占/结算/退款时点；失败部分成功与取消规则；欠费字段含义；服务端舍入；积分过期跨时区规则；充值最低金额与精度；券叠加；订阅地区范围；管理员权限矩阵。这些空缺没有用经验补写为事实。
