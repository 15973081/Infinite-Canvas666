## 本次需求确认与交付边界

管理平台单独迁出：拥有独立前端产物、API 入口、进程及部署配置。首版沿用同一仓库和统一 PostgreSQL 身份/权限服务；不要求拆成两个仓库，也不复制成员及授权数据。业务工作台停止后，数据库正常时管理平台仍可登录和控制维护。

| 用户操作 | 预期结果 | 当前交付情况 |
|---|---|---|
| 创建空间并分配成员 | 成员只看到获授权空间，同一成员可加入多个空间 | 管理页面和基础隔离已验收，全部业务路径及正式迁移仍待完成 |
| 新增角色并配置权限 | 例如设计空间的“美术”可编辑、审核空间的“审核员”只查看；角色在各自空间授权 | 自定义角色、分配、版本检查及停用替代已验收 |
| 调整成员角色或移出空间 | 后续访问和编辑按最新授权判定，不能靠旧页面继续写入 | 后端复验和首批客户端已接入，完整撤权联调待完成 |
| 配置供应商并分配空间 | 后台维护凭证，成员只使用获分配服务 | 配置/加密/分配、模型列表检测及智能画布摘要已验收，协议诊断已验收，旧配置导入和完整生成联调待完成 |
| 维护指定空间 | 只限制该空间，展示公告并允许已有操作按截止时间收尾 | 状态控制和页面已验收，完整排空与恢复待完成 |
| 维护整个平台 | 平台限制覆盖全部空间，重启不自动开放 | 持久状态已接入，完整发布与恢复演练待完成 |
| 在后台处理画布占用 | 有接管权限的管理员明确目标并填写原因，操作留审计 | 租约后端和工作台接管控件已接入，后台管理视图待完成 |

画布工具栏继续承担开始编辑、保存结束、申请交接和草稿处理；独立后台负责空间、角色、维护以及受控管理操作。普通编辑权限与管理员接管权限分开，不再用 IP 或局域网设备名判断身份。

迁出按功能逐项验收：先迁移供应商与连接配置，再补任务处置和备份管理，最后移除工作台旧管理页面并核验旧 API 无授权旁路。每项需同时验证管理站点可用、工作台必要业务摘要仍可用、无权限访问被拒绝；临时关闭旧接口不算迁移完成。本地验收继续使用 `.local/cloud` 的 PostgreSQL 隔离 schema 和对象模拟。

## 1. 产品边界

| 产品 | 使用者与职责 |
|---|---|
| 画布工作台 | 成员登录、选择获授权空间、使用普通/智能画布、素材、任务、画布锁与交接；显示维护公告和保存状态 |
| 独立管理平台 | 成员管理、空间创建与分配、角色管理、权限配置、维护、运行状态、供应商管理、备份记录及操作审计 |

这里的“空间”指协作工作空间，每个空间有自己的画布、素材目录、提示词、任务、历史和费用视图。成员可以被分配到多个空间，在不同空间承担不同角色。空间不是磁盘目录，也不等于仅在前端增加一个筛选标签。

同一空间内仍采用“单人编辑、多人查看”。个人账号全平台唯一；跨空间访问必须重新核验成员关系。空间内个人对话保留成员级访问边界，不因加入空间而自动公开。

首版纳入：独立管理入口和部署单元、多空间、空间分配、自定义角色与权限点、画布锁联动、维护控制及必要审计。暂不纳入公开注册、角色继承/显式拒绝表达式、逐节点权限、跨空间实时共享、计费套餐/余额、自动扩容、任意远程命令执行或自动云发布。

## 2. 独立迁出的技术边界

部署方式按“独立管理站点与进程，复用统一的身份、权限及数据服务实现”规划；这是本次采用的默认部署方案。若后续明确要求管理前后端完全独立服务，再调整服务边界，空间、权限和维护的数据规则保持一致。

- 管理前端有独立目录、构建入口、路由和发布产物；工作台不再打包或挂载完整管理页面。迁出后的必要成员入口通过链接打开管理站点。
- 管理 API 使用独立入口/进程和路由集合，业务 API 保持现有入口；首版可放同一仓库、同一主机，复用 Python 权限/存储模块和 PostgreSQL，避免两份不同的授权逻辑。若选择管理前后端完全独立服务，再将模块边界调整为明确的服务契约。
- 本地使用各自回环端口，沿用 `.local/cloud` 对象模拟。生产域名和端口在部署阶段配置，本次不创建域名或暴露新服务。
- 两个站点共享成员身份模型，但各自使用作用域明确的会话 Cookie；不得在 URL 中传会话令牌或为方便而给所有子域共享管理员 Cookie。首版允许分别登录；后续单点登录需正规短期授权交换。
- 管理 API 的入口、角色和目标空间均在服务端校验。删掉工作台上的管理按钮不等于完成权限迁移；旧管理路径也须移除或受同一授权规则保护，不能保留旧共享认证旁路。
- 独立管理进程不启动业务生成消费者，不复用会把维护状态重置为 normal 的业务启动流程。停止业务 Web 进程后，管理站点仍能读取持久维护状态并显示业务离线。
- PostgreSQL 或公共身份服务不可用时，管理平台明确显示不可用并拒绝变更；独立部署不保证公共依赖故障时仍能执行操作。
- 后台不直接执行任意 shell、不通过网页运行任意 SQL。服务重启、代码发布和数据库迁移仍由受控运维流程执行，管理平台提供维护准备和状态确认。

现有保留供应商配置、维护控制等管理功能需逐项盘点后迁出。工作台仍可读取当前成员有权使用的模型/服务摘要，不能因此获得原始密钥或管理权限。素材选择、画布内编辑等业务工具留在工作台；后台提供有权限的空间资源管理视图。

## 3. 空间与数据隔离

### 分配流程

1. 平台管理员创建空间，设置名称、说明、初始空间管理员和启用状态。
2. 将已有成员分配到空间，并授予一个或多个该空间角色；分配与撤销均留审计。
3. 成员登录后只看到所属且可访问的空间；没有空间时显示“尚未分配空间”，不回退到 default。
4. 工作台切换空间时清空旧空间视图缓存、实时订阅及临时选择状态；未保存草稿须先处理。草稿和续传状态按成员、空间、画布及编辑会话隔离。
5. 撤销成员空间资格后，后续读取、签名、续租及写入立即按新权限判定；撤销该空间的编辑资格与订阅，不影响其其他空间合法权限。

### 存储改造

迁移起点是仅接受 default 的存储配置，以及多处写死 `workspace_id='default'` 的查询、任务、文档和账本代码。当前已有请求/worker 空间上下文与首批仓库隔离；启用多空间前仍必须完成全部访问路径盘点及迁移，不能仅放开配置校验。逐批证据见实施记录。

- 请求中的空间 ID 只作选择参数，服务端由成员关系验证并建立请求范围；不使用进程级环境变量切换当前用户空间。
- 所有画布、素材、目录、任务、账本、备份、历史、对话和旧路径解析查询限定目标空间。后台跨空间查询走显式管理权限，不能拿普通 API 的缺省范围实现全表读取。
- 复合唯一约束、外键和引用校验防止跨空间引用；画布锁、交接请求和任务幂等键都包含空间。异步消费者从持久任务记录恢复空间，不能依赖提交者最后一次选择的空间。
- 全局成员资料与空间成员关系分开；角色定义、角色授予及维护状态明确平台/空间作用域。
- TOS 新对象使用空间对应前缀，资产签名与旧路径别名先校验所属空间。前缀只辅助组织，不能替代权限检查。已发出的签名链接在有效期内仍可能使用；缩短有效期，不能宣称撤权立即撤销既有签名。
- 后台查看空间的存储量、任务量、成员数和备份状态；容量配额规则预留字段，暂不实现套餐扣费或跨空间自动资源再分配。
- 空间首版提供停用/归档，不提供一键物理清空原件。跨空间移动/复制另设显式流程；本轮不默认共享或移动已有素材、账本和任务。
- 费用数据按空间展示，历史金额、价格快照和去重指纹保持不变。平台管理员也不能通过成员角色修改历史收费事实。

## 4. 可新增角色的权限模型

采用权限点 RBAC：角色是权限点的组合，角色名称可改，业务代码按权限点判定。首版不做角色继承与显式 deny；同一作用域多个有效角色的允许权限取并集，成员/空间停用和维护限制始终优先。

| 层级 | 职责和示例 |
|---|---|
| 平台角色 | 平台超级管理员、运维管理员、审计员；管理空间创建、全局成员、平台维护等明确授权范围 |
| 空间角色 | 空间管理员、编辑者、查看者为内置模板；可新增“美术”“审核员”“素材管理员”等自定义角色 |

创建角色时选择可授予的权限点和作用域。权限目录由应用定义，后台不能自造任意命令或后端不存在的权限。授予者只能在自己的可委派权限和目标空间内授予权限，不能把“管理角色”变成自行提权入口；平台超级管理员属于受保护角色，普通空间管理员不可创建等价角色或授予平台权限。

| 权限点示例 | 作用 |
|---|---|
| space.create / space.assign / space.archive | 创建空间、分配成员、归档空间；平台范围 |
| space.members.manage / space.roles.manage | 管理指定空间成员及可委派的空间角色 |
| canvas.read / canvas.create / canvas.edit / canvas.delete / canvas.restore / canvas.export | 分别控制画布读取、新建、编辑、删除、恢复、导出 |
| canvas.lock.takeover | 受控接管指定空间画布；与普通编辑权限分开 |
| asset.read / asset.upload / asset.manage / prompt.manage | 素材、目录及提示词操作；无需绑定无关画布锁 |
| generation.submit / task.read / task.review | 发起生成、查看任务、核对异常任务；人工重试仍遵守“不盲目付费重提”限制 |
| provider.use / provider.configure | 使用获分配的供应商配置与修改配置分开；原始密钥不返回浏览器 |
| maintenance.space / maintenance.platform | 空间维护与全平台维护分开；空间角色不可控制平台维护 |
| audit.read / backup.read / backup.request | 查看审计、查看备份记录、发起受控备份任务；数据库恢复不等于普通后台按钮权限 |

空间角色只操作所属空间的备份记录或受控导出；全库备份及恢复属于平台运维范围，不向空间管理员暴露其他空间数据。

内置角色模板受保护，允许复制为自定义角色。删除或停用已授予的角色前展示影响成员并要求指定替代/撤销方案；更改与绑定更新使用事务。不得删除/停用最后一个有效平台超级管理员；首版每个启用空间也至少保留一个有效空间管理员。

保存角色和成员授予时递增授权版本；API、编辑租约和 worker 在关键操作重新校验。缓存使用授权版本失效，不依赖重新登录才更新权限。平台管理员的跨空间操作必须明确目标并记审计；“有管理平台入口”本身不授予所有资源正文和密钥读取权限。

## 6. 支持维护的行为协议

### 平台维护与空间维护

平台维护约束全部空间；空间维护只约束目标空间。有效限制取更严格者：空间恢复不能解除仍有效的平台维护。计划时间、状态、发起者、原因、公告、状态版本及恢复时间存 PostgreSQL，并发更新做版本检查和审计。

| 状态 | 工作台及任务行为 |
|---|---|
| normal | 按角色及画布锁正常操作 |
| scheduled | 展示维护时间/范围，提醒保存；在计划到达前继续正常权限规则 |
| draining | 停止新生成提交、新上传会话、新编辑租约及其他新增业务写入；仅开放既有操作收尾清单，已持锁页面在明确截止时间前可保存及受限续租，已有上传可在宽限内确认 |
| read_only | 允许查看/预览/导出，禁止用户共享数据写入及新付费任务；草稿保留在个人端 |
| offline | 面向普通成员显示维护页，拒绝业务访问；管理入口及最小维护状态接口仍可用 |
| recovering | 运维复核业务、数据库、素材和队列状态，保持限制；管理员明确确认后才回 normal |

draining 中已有上游任务继续查询、输出入库和费用记录；尚未付费提交的队列任务暂停。结果落库等受控内部操作不使用普通成员写入接口。read_only/offline 同样允许已提交任务完成必要持久化，避免维护导致已付费结果丢失；原地数据库迁移或停止 worker 必须等任务排空或进入已验证可恢复状态，不能把“页面只读”当作“数据库已无写入”。

- 从 draining 进入下一限制状态前展示在途生成、上传、待保存页面和当前锁数量；管理员看不到尚未上报的本地修改，不能声称替所有人保存。
- 到截止时间后旧编辑会话停止共享写入并保留草稿；不能因隐藏浏览器标签页没收到公告而继续绕过后台限制。
- 计划维护由持久调度记录驱动，多个执行者竞争只执行一次；进程重启后按数据库时间补核对，不能仅使用网页 setTimeout。
- 状态改变通过持久事件或带版本的查询同步到业务进程和 worker。拒绝新操作以服务端数据库状态为准，WebSocket 提醒及进程缓存仅为加速。
- 重启不能自动解除维护。现有 `mark_service_started()` 会恢复 normal，升级时须替换为显式恢复流程。
- 管理端的维护权限替代当前仅接受 127.0.0.1 的控制方式；保留明确受控的本机恢复手段，不能把“来自局域网/本机”当作平台角色。
- 数据库恢复/版本发布由运维执行；管理平台可检查备份和排空前置条件，但不承诺直接替代云平台部署工具。

## 7. 数据模型与模块拆分

建议在原协作数据模型上增加 `roles`、`permissions`、`role_permissions`、`platform_member_roles`、`workspace_member_roles`、`maintenance_windows`、`management_events` 和必要的任务/事件记录；成员关系与角色绑定分表，允许同一成员在多个空间拥有不同角色。

内置 workspaces 表继续沿用，扩展状态和管理信息；所有新表按作用域约束外键/唯一键。schema 变更采用追加 migration，不改写 001–003。统一授权服务向业务接口、管理接口和 worker 提供 `member + action + workspace + resource` 判定，禁止把“是否管理员”散落成多份条件判断。

建议模块按管理前端、管理 API 入口、共享身份/权限模块、空间仓库、维护协调器拆分；迁移脚本、测试和运维入口分别独立。目录名在实施时根据现有构建条件确定，不以本计划创建空壳工程冒充完成。

## 8. 执行顺序与既有画布锁计划

| 顺序 | 阶段 | 主要交付 | 状态 |
|---|---|---|---|
| 1 | M1 + C1：身份、空间、权限基础 | 成员会话、多空间数据范围、自定义角色、授权服务、历史身份映射；盘点全部 default 硬编码和旧管理入口 | 进行中：服务基础完成，业务接入待完成 |
| 2 | M2：管理平台独立迁出 | 独立构建/入口/进程；成员、空间、角色界面；迁出已有管理能力；旧入口关闭或统一鉴权 | 进行中：独立入口、成员/空间/角色及供应商配置分配已验收，模型检测及只读协议诊断已接入，旧配置、任务、备份及完整迁出待完成 |
| 3 | C2：数据库画布锁 | 租约、锁代次、写入校验、接管和任务回填，全部绑定成员与空间权限 | 进行中：租约、写入约束与指定交接后端已验收，完整联调待完成 |
| 4 | C3：双画布协作体验 | 空间切换、身份展示、多人查看、交接、草稿与断线恢复 | 进行中：编辑、交接、草稿恢复/清理/副本已接入，实时名单及完整故障联调待完成 |
| 5 | M3：维护中心 | 平台/空间维护、公告和计划、排空及恢复、任务与锁联动、跨进程状态同步 | 进行中：控制底座、有效租约统计、页面报告及人工核对已验收，完整排空、任务处置及恢复待完成 |
| 6 | M4：迁移与完整验收 | 至少两空间、多成员和自定义角色、角色撤销竞态、维护、备份恢复及浏览器验收 | 未开始 |

以上为集成顺序；M3 的权限点和状态协议在 M1 设计时确定，避免 C2/C3 先实现无维护约束的旁路。每阶段按可验收变更独立提交 Git，不将只搭建管理页面或新增角色名称视为功能完成。

## 9. 迁移与验收门槛

已有 default 保留为迁移后的一个空间，旧记录继续归属该空间，不自动复制到所有新空间；成员分配必须明确。旧 ID、对象 key/version、费用记录和原始日志保留。默认空间的旧素材别名只在该空间内解析。迁移报告包含各空间资源数量、未知成员归属、角色授权和跨空间引用异常。

启用前关闭旧共享认证和旧管理旁路，撤销旧会话/编辑凭证；备份恢复后要求重新登录及领取锁，维护状态不能因恢复或启动被自动清空。已有新写入后的回退须保全增量，不能靠恢复旧单空间代码绕过新隔离规则。

| 验收组 | 必须通过 |
|---|---|
| 独立平台 | 工作台不再承载管理页面；管理进程独立启动，业务停止后仍能显示维护状态；共用数据不会产生双写分叉 |
| 空间隔离 | A 空间成员猜测 B 的画布/素材/任务/备份/签名/对话 ID，API 与 WebSocket 都拒绝；并发请求及 worker 不串空间 |
| 角色管理 | 创建、修改、分配、停用自定义角色；只授予允许范围；无法自提权、跨空间授权或删除最后管理员 |
| 权限变更 | 撤权与保存/续租/新付费提交竞争，服务端按一致事务规则判定；已提交任务结果仍可安全持久化 |
| 画布锁 | 原 C2/C3 验收矩阵在两个空间重复执行；角色变化和维护切换后旧代次不能继续写入 |
| 维护 | 计划按时生效、重启不解除、平台限制优先、空间互不干扰、旧客户端无法绕过、排空失败不谎报可发布 |
| 管理迁移 | 本机维护限制升级、旧管理路径及共享 Basic 不能旁路、新进程不会重复启动任务消费者 |
| 恢复与审计 | 新数据库恢复后成员/空间/角色/画布/费用完整，旧凭证失效；授权、维护和接管可回溯，不记录秘密 |
| 端到端 | 两空间、至少三成员、自定义角色、普通/智能画布及独立管理平台实际浏览器验收通过 |

全部开发验收先在 `.local/cloud` 的隔离 PostgreSQL schema 和本地对象目录完成；不调用真实付费模型。原 52 项云集成、120 项 Python、158 项 CJS 是历史存储基线，实施时新增专项测试并运行全量回归后记录实际结果。本次文档更新不代表这些新验收已经执行。
